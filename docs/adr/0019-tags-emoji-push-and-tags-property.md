# 0019 – Tags and emoji: push via the metaHash, the `tags` property stays page content

- Status: accepted
- Date: 2026-10-17
- Related: architecture §6.2, §7.5, §10.2, milestone M6, issue ONC-7 (M6)

## Context

M3 writes emoji and tags from the server into the note (`nc_emoji`, `nc_tags`, `metaHash`). M6 adds the opposite direction and the option `tagsProperty`. Open questions: How does the run recognize that the user changed emoji or tags without extending the planner with file contents? What applies to the page text with `tagsProperty = tags`? What happens to the tags when moving to another collective?

## Decision

- **Detection in the executor, not in the planner.** A note with changed fields has a new mtime, so the planner already plans `push` (or `update`) for it. The executor reads the file there anyway; `executorMeta.ts` compares the note's emoji and tags with the `metaHash` of the state (tags first mapped to the server's spelling). The scan stays cheap, the planner pure. The idle run reads no additional files.
- **Same decision as for content** (at the user's request, 2026-10-17; replaces the rule "remote wins" from architecture §7.5 and the first version of this ADR). `decideMeta` calls `decideContent` on the hashes of emoji and tags: base = `metaHash` in the state, local = fields of the note, remote = hash of the server values. Only the note changed → push to the server, afterwards the run rewrites the `nc_*` fields in the server's spelling. Only the server changed → its values into the note. Both equal → only the base advances. Both different → `conflictStrategy`: `preferLocal` pushes, `preferRemote` takes the server values, `conflictFile` leaves the note unchanged, creates a conflict copy with the server values (`nc_emoji`/`nc_tags` without page ID) and sets the page to `conflict`; the `metaHash` advances to the server values in the process. The conflict dialog applies unchanged: "Keep local" pushes the note's values in the next run, "Take remote" sets the `metaHash` to the note's values so that the next run takes the server values. A page that is already waiting as a conflict is not touched again. If an `update` pulls a remote text, the note's changes go to the server first (or, with `conflictFile`, stay in the file).
- **The `metaHash` no longer contains the title** (`metaHash(emoji, tags)`): This is the only way to answer "did the user change it?" from hashes without knowing the earlier title. A rename is a structural change anyway (M5). Stored hashes from M3–M5 no longer match, once: if note and server agree, only the base advances; otherwise the server wins (an unknown base `''` always takes the server values).
- **Tag creation.** Names are checked case-insensitively against the collective's tag cache (exact match first), only missing tags are created with color `0082c9`. If the server rejects as a duplicate (another client was faster, different collation), the run re-reads the tags and uses the existing one. The cache in the state is kept up to date.
- **Removing the emoji** sends `""`: The server ignores a JSON `null` (test server Nextcloud 33; response `emoji: null`, the next `GET` returns the old emoji; corrects M0). `""` is read like `null`.
- **Tags only in Obsidian's `tags`** (at the user's request, 2026-10-17; replaces the option `tagsProperty` and the field `nc_tags`): The tags live in exactly **one** property. The option only brought the separation of private Obsidian tags from Collectives tags and exact names with spaces, but cost mode switching, double paths and confusion (two properties, one "tags" block in Collectives). Implementation: The sync converts names. A space in a Collectives tag becomes `-` in Obsidian, a `-` stays `-`, a new `-` in Obsidian is created as `-` (never as a space). Reverse mapping `findTagByName`: first the tag with exactly this name, otherwise the one whose name looks the same with `-` for spaces, ignoring case. `tags` is read as a flow list, block list or scalar; if the property is missing, the page has no tags (deleting the property removes the tags); if it is in an unread form (flow list over several lines), the rule is: no change. Like `nc_*`, `tags` is a managed field and is **not** uploaded (`toRemote`/`canonicalRemote`); the tags appear in Collectives only as tags. *Earlier versions of this ADR* (option, text property, mode switching in the state) are thereby superseded.
- **Notes from before the change:** If a note still has `nc_tags` and no `tags` property, its names count (so the first sync does not remove a tag). On the next write of the fields, `tags` replaces the old `nc_tags`.
- **New note with tags/emoji:** When the page is created, the note's values go to the server; they are not overwritten by the `nc_*` fields.
- **Moving across collectives:** The tags are lost server-side (api-notes). After the move, the run reassigns the tags of the note (and of the subpages with a file) in the target collective and creates missing ones. If that fails for a subpage, the next run takes over the server's metadata.

- **`#tags` in the text:** `readLocalFields` supplements the tags of the property with the `#tags` of the text (excluding code, headings, links; `src/mapping/tags.ts`, `inlineTags`). They go to the server as tags and then appear in the property. Inline tags **only add**: If you remove a `#tag` from the text, it stays in the property and on the page; whoever wants to get rid of it deletes it there. The text itself is never rewritten.
- **Display instead of renaming (presentation only):** The properties keep their technical keys. In the properties view, the plugin hides the key field of `nc_page_id` etc. and puts a localized name there (Page ID, Collectives tags, …; `src/ui/propertyLabels.ts`, DOM instead of a CSS variable, because the result can be verified that way). The page's emoji appears in front of the title in the file list, note header and inline title (`src/ui/emojiTitles.ts`, setting `showEmojiInTitles`); the file name stays unchanged. Both rely on Obsidian's DOM classes (non-public interface) and fall back to the normal display if they change. Tab titles are not supplemented (no public access).

- **Values as Obsidian's properties view writes them** (addendum 2026-10-17, bug in the manual test: an emoji that was set did not arrive): The view writes `nc_emoji: 🚀` without quotation marks and lists as block lists; the plugin only read JSON (`"🚀"`, `["A"]`) and interpreted everything else as "no emoji, no tags". Now `frontmatter.ts` reads YAML scalars (plain, `"…"`, `'…'`) and lists (flow, block, scalar).
- **Property `Emoji` by hand:** Whoever creates a property `Emoji` (any capitalization) means the page's emoji. It is read (`nc_emoji` takes precedence), replaced by `nc_emoji` on the next write of the fields and never uploaded.
- **Validation:** An emoji is exactly one emoji (including skin tone, ZWJ sequence, flag, keycap; `src/mapping/emoji.ts`, pure regex). Anything else (text, several emojis) is **not** sent; the note stays unchanged, the run reports it as a warning (`SyncResult.metaInvalid`). Obsidian's properties view has no type check for plugin fields, so the plugin checks during sync.
- **Emoji picker:** The command "Set page emoji" opens a dialog (input with validation, grid of common emojis, "Remove emoji") and writes `nc_emoji` via `processFrontMatter`. It also opens when the user creates an empty property `Emoji` in the current note (best approximation: Obsidian offers no hook for creating a property).

- **Hiding properties (default):** The `nc_*` properties are technical and not meant to be edited by the user. The setting `hidePluginProperties` (default on) hides them in the properties view via a CSS class on the `body`; set the emoji with the command or the context menu, tags are in `tags`. If it is off, localized names show the properties.
- **Context menu and commands:** "Set page emoji" and "Rename page" are in the file menu (note or folder of a folder page) and in the editor menu. Renaming (`src/mapping/renamePage.ts`) renames, for a page with subpages, the note **and** its folder together (`Folder/Name/Name.md` → `Folder/New/New.md`) via `fileManager.renameFile` (links are adjusted), checks beforehand for existing names and does not apply to the start page of a collective (its name is that of the collective, only an admin renames the folder). The next sync transmits the rename like any local rename (ADR 0018).

- **Display in the file list (presentation only):** A folder shows the emoji of its own note (`Folder/Folder.md`), and this note is listed first in its folder, regardless of Obsidian's sorting (`.nav-file[data-nc-folder-note]` with `order: -1`, `src/ui/emojiTitles.ts`; no interference with file names or DOM order, setting `folderNoteFirst`). This relies on Obsidian's DOM classes (non-public) and falls back to the normal display if they change.

## Alternatives considered

- Read local metadata in the scan and compare in the planner: reads every file on every run, contradicts the idle-run goal (M9).
- Second field `nc_tags` next to `tags` (option `tagsProperty`): allows private Obsidian tags and exact names with spaces, but costs mode switching and confusion; rejected by the user.

## Consequences

- `SyncResult.metaPushed` counts changes sent; the notice mentions them.
- A tag change is not a content change: `tags` is not uploaded. Existing pages whose text already carries a `tags:` frontmatter keep it on the server until someone deletes it; the run compares without these lines.
